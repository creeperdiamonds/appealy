# Apex Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `creeperdiamonds.xyz` serves a personal site with Appealy on it, and a Tebex reviewer landing anywhere in the estate reaches everything a review needs in one hop.

**Architecture:** One Cloud Run service serves both hosts, split by nginx `server_name`. The apex gets its own static root with no API proxying. The Tebex page assembles existing claims by linking to them rather than restating them, so there is one copy of each and no second version to drift.

**Tech Stack:** Static HTML, no JavaScript, no build step · nginx (envsubst template) · Docker · Cloud Run · Cloudflare DNS

**Spec:** `docs/superpowers/specs/2026-08-27-apex-site-design.md`

## Global Constraints

- **`site/` and `home/` are static HTML with no JavaScript and no build step.** `site/index.html`'s own header gives the reason: a marketing page that renders blank while a bundle downloads is a marketing page that loses the visitor. Do not add either.
- **`home/index.html` stays fully self-contained** — inline styles, inline mark, no reference to `/brand/` or `site.css`. `landing/README.md` argued this so the page drops onto any host unchanged, and a personal site is the artifact most likely to move.
- **The existing nginx `server` block must keep answering every non-apex Host** — the Appealy subdomain, the `run.app` URL, and Cloud Run's health probe. It has no `server_name` today, so it answers all of them by default; `default_server` is what preserves that once a second block exists.
- **The apex block proxies nothing.** No `/api/`, no `/auth/`, no `/dashboard/`. A personal page has no reason to reach the API, and not proxying means a misconfigured apex cannot become a second door to the console.
- **Links stay extensionless.** `location / { try_files $uri $uri.html $uri/ =404; }` resolves `/tebex` to `tebex.html`, matching how `/pricing` and `/terms` are already linked.
- **Docker is not installed on this machine.** The nginx change cannot be tested in a container locally; Task 3 carries the post-deploy verification and rollback procedure instead.
- House style is comments that explain *why*, often at length.
- Commit after every task.

### Task 3: nginx routing

**The one task in this plan that can break production.** The existing `server` block has no `server_name`, so it currently answers every Host: the Appealy subdomain, the `run.app` URL, and Cloud Run's health probe. In nginx, when no `server_name` matches, the request goes to whichever block is marked `default_server` — and if none is, to the **first block in the file**.

**Files:**
- Modify: `web/nginx.conf`
- Modify: `web/Dockerfile` (one `COPY` line)

**Interfaces:**
- Consumes: `home/index.html` from Task 2.
- Produces: the apex Host served from `/usr/share/nginx/html/home`; every other Host unchanged.

- [ ] **Step 1: Mark the existing block as default**

`web/nginx.conf:43` currently reads `listen ${PORT};`. Change it to:

```nginx
  # default_server is load-bearing now that a second server block exists
  # below. It keeps every Host that is NOT the apex answering exactly as it
  # does today: the Appealy subdomain, the run.app URL, and Cloud Run's
  # health probe, which arrives with no Host worth matching.
  #
  # Without it, nginx falls back to the FIRST block in the file — which
  # would work by accident today and break the moment the blocks are
  # reordered.
  listen ${PORT} default_server;
```

Change nothing else in this block.

- [ ] **Step 2: Add the apex block**

After the closing `}` of the existing server block (line ~159, the last line of the file), append:

```nginx

# ---------------------------------------------------------------------------
# The apex, creeperdiamonds.xyz.
#
# Same container, same port, different root — split on Host rather than run
# as a second Cloud Run service, because a personal page has no traffic worth
# insulating and a second service is another image, another deploy path, and
# another thing to forget to update.
#
# Deliberately proxies NOTHING. No /api/, no /auth/, no /dashboard/. The page
# has no reason to reach the API, and not proxying it means a misconfigured
# apex cannot become a second, unintended door to the console.
# ---------------------------------------------------------------------------
server {
  listen ${PORT};
  server_name creeperdiamonds.xyz;
  root /usr/share/nginx/html/home;
  index index.html;

  # Same policy as the main block. Repeated rather than shared because nginx
  # add_header does not inherit into a block that sets its own, and an
  # include file would split a short policy across two files to save a few
  # lines.
  add_header X-Content-Type-Options "nosniff" always;
  add_header X-Frame-Options "DENY" always;
  add_header Referrer-Policy "strict-origin-when-cross-origin" always;

  location = /index.html {
    add_header Cache-Control "no-cache";
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
  }

  location / {
    try_files $uri $uri.html $uri/ =404;
  }
}
```

**Read the existing block's `add_header` lines first and match them.** The set above is what the spec expects; if the live config carries different or additional headers, copy those instead — the apex should not have a weaker policy than the site next to it.

- [ ] **Step 3: Copy the root into the image**

`web/Dockerfile:76` copies `site`. Add after the `status` copy:

```dockerfile
# The apex page, served by the server_name block in nginx.conf on
# creeperdiamonds.xyz only. Self-contained, so it needs nothing else copied
# alongside it.
COPY home /usr/share/nginx/html/home
```

- [ ] **Step 4: Syntax-check what you can**

Docker is not installed on this machine, so the container cannot be built and tested locally. Do what is possible:

```bash
command -v nginx >/dev/null && nginx -t -c "$(pwd)/web/nginx.conf" || echo "nginx not available locally — skipping syntax check"
```

That will likely report nginx as unavailable, and will fail on `${PORT}` even if present, since the file is an envsubst template rather than a finished config. Confirm by eye instead: braces balanced, both `server` blocks closed, exactly one `default_server` in the file:

```bash
grep -c 'listen .*default_server' web/nginx.conf   # expect 1
grep -c "^server {" web/nginx.conf        # expect 2
```

- [ ] **Step 5: Commit**

```bash
git add web/nginx.conf web/Dockerfile
git commit -m "Serve the apex from the same container, split on Host"
```

- [ ] **Step 6: Deploy, then verify within the minute**

This change is verified in production because it cannot be verified anywhere else. Deploy:

```bash
gh workflow run deploy-merged.yml --ref main -f migrations=skip
```

`migrations=skip` — this change touches no schema, and running migrations that have already run is a needless risk on a routing deploy.

The moment the run reports success, check the paths that must not have moved:

```bash
for p in / /pricing /dashboard/ /status /api/health; do
  printf '%-14s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' https://appealy.creeperdiamonds.xyz$p)"
done
```

`/`, `/pricing`, `/dashboard/` and `/status` must return `200` or `30x`. **Any `404` on `/dashboard/` means `default_server` is wrong and the console is down.**

- [ ] **Step 7: Know the rollback before you need it**

If any path above regressed, roll traffic back immediately rather than debugging live:

```bash
gcloud run revisions list --service=appealy --region=us-central1 \
  --project=yahav-project-505809 --format="value(metadata.name)" --limit=2

gcloud run services update-traffic appealy --region=us-central1 \
  --project=yahav-project-505809 --to-revisions=<PREVIOUS_REVISION>=100
```

Traffic migration is near-instant and does not rebuild anything. Fix forward afterwards, not before.

### Task 5: Map the domain

Manual and one-time. `deploy-merged.yml` deploys the service; it does not create domain mappings, and it should not — a mapping is created once and a deploy runs many times.

**Files:**
- Modify: `DOCKER.md` or `README.md` — wherever deployment steps are documented; find it with `grep -rln "domain-mappings\|creeperdiamonds.xyz" --include="*.md" .`

**Interfaces:**
- Consumes: Tasks 1–4 deployed.
- Produces: `creeperdiamonds.xyz` serving `home/index.html`.

- [ ] **Step 1: Confirm the About paragraph was written**

```bash
grep -n "AUTHOR:" home/index.html
```

**If this still returns a hit, stop.** The placeholder from Task 2 is still in the page and the site would go live saying `[About text goes here.]`. This is the last gate before a real domain points at it.

- [ ] **Step 2: Confirm `contact@` receives mail**

Send a message to `contact@creeperdiamonds.xyz` and confirm it arrives. Only `real@creeperdiamonds.xyz` is known to work; `contact@` may need a Cloudflare Email Routing rule. A published address that bounces is worse than none, because the sender believes they reached someone.

- [ ] **Step 3: Create the mapping**

```bash
gcloud beta run domain-mappings create \
  --service=appealy \
  --domain=creeperdiamonds.xyz \
  --region=us-central1 \
  --project=yahav-project-505809
```

It prints the DNS records to add. An apex cannot use a CNAME, so expect **A and AAAA records** rather than the CNAME the subdomain uses.

- [ ] **Step 4: Add the records in Cloudflare**

Add exactly the records printed. If the zone already has A records at the apex, replace them — two sets will resolve unpredictably.

Set them to **DNS only** (grey cloud), not proxied. Cloud Run issues and renews its own certificate against those records, and a proxied record puts Cloudflare's certificate in front of that process.

- [ ] **Step 5: Wait, then verify**

The Google-managed certificate takes up to roughly fifteen minutes after DNS propagates. Then:

```bash
curl -s -o /dev/null -w "apex        %{http_code}\n" https://creeperdiamonds.xyz/
curl -s https://creeperdiamonds.xyz/ | grep -c "creeperdiamonds"
curl -s -o /dev/null -w "appealy     %{http_code}\n" https://appealy.creeperdiamonds.xyz/
curl -s -o /dev/null -w "dashboard   %{http_code}\n" https://appealy.creeperdiamonds.xyz/dashboard/
```

The apex must serve the new page; the Appealy subdomain and dashboard must be untouched. Confirm the apex is serving `home/` and not `site/` — if it returns the Appealy marketing page, `server_name` did not match and the request fell through to `default_server`.

- [ ] **Step 6: Document it**

Add the mapping to the deployment docs: the command, that the apex needs A/AAAA rather than CNAME, that the records are DNS-only, and that this is done once rather than per deploy.

- [ ] **Step 7: Commit**

```bash
git add -A
git commit -m "Document the apex domain mapping"
```
